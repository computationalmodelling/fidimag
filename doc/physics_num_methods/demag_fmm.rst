FMM/Barnes-Hut Demagnetising Field
==================================

The dipolar (demagnetising, stray field) interaction, defined in
:doc:`core_eqs`, is a sum over every pair of spins in the system, so a direct
evaluation costs :math:`O(N^2)` per field update. Fidimag currently offers two
ways of avoiding that cost for atomistic simulations: ``Demag``, which uses
OOMMF's FFT convolution, and ``DemagFMM``, which uses a hierarchical tree
method (a genuine Fast Multipole Method, or the cheaper Barnes-Hut
approximation to it). Both live in ``fidimag/atomistic/demag.py``.

FFT-based Demag
----------------

``Demag`` only works on a ``CuboidMesh``: the regular, translationally
invariant lattice lets the pairwise interaction be written as a convolution
of the spin configuration with a fixed dipolar tensor, which is then
evaluated with an FFT. This is what most atomistic simulations use day to
day, and it is very fast, but it needs the mesh to be a full rectangular
grid, including every non-magnetic (:math:`\mu_s=0`) site inside the padded
region - there is no way to leave a site out of the grid.

FMM/Barnes-Hut Demag
---------------------

``DemagFMM`` instead builds an octree over the spin positions and evaluates
the field by tree traversal, following the recursive approach of Visscher
and Apalkov [1]_. Groups of spins far from a given site are approximated by
a truncated multipole expansion rather than summed individually, which is
what gives the method its (better than :math:`O(N^2)`) scaling. Two
variants are available through the ``type`` argument:

- ``type='fmm'`` - a full Fast Multipole Method: multipole expansions are
  translated down to local expansions at every level of the tree (M2L), so a
  well-separated group only needs to be visited once, however deep the tree.
- ``type='bh'`` - the cheaper Barnes-Hut approximation: multipole
  expansions are evaluated directly at the target (M2P) rather than
  translated first, which is simpler but revisits well-separated groups at
  every target rather than translating once per group.

Three parameters control the approximation:

- ``order`` - the truncation order of the multipole/local expansions.
  Higher order is more accurate and more expensive per interaction. Valid
  values are whatever ``fidimag/atomistic/fmmlib/operators.cpp`` was
  actually generated for, exposed as ``fidimag.extensions.fmm.MINORDER`` and
  ``MAXORDER`` (currently 2 and 13, i.e. orders 2 to 12 inclusive);
  ``DemagFMM`` validates against these directly rather than a fixed range.
- ``ncrit`` - the maximum number of spins in a tree leaf before it is
  subdivided further.
- ``theta`` - the multipole acceptance criterion. A group of spins is
  approximated as a single expansion once it is far enough away relative to
  its size, with "far enough" set by ``theta``. ``theta=0.0`` disables the
  approximation entirely and falls back to an exact pairwise sum (used as
  the correctness baseline in ``tests/test_demag_fmm.py``); larger ``theta``
  accepts coarser approximations further down the tree, which is faster but
  less accurate.

The underlying tree and multipole/local operators are generated by
`fmmgen <https://github.com/rpep/fmmgen>`_ [2]_, which derives the operator
expressions symbolically with SymPy for whatever expansion order is
requested, rather than relying on hand-derived formulae (impractical much
past third order). The generated code
(``fidimag/atomistic/fmmlib/operators.cpp``/``.h``) is committed directly
into the repository and compiled as part of the normal CMake build; fmmgen
itself is a build-time code generator, not a runtime dependency.

Harmonic compression
~~~~~~~~~~~~~~~~~~~~~

By default (``compressed=True``), ``DemagFMM`` uses fmmgen's trace-free
("harmonic-compressed") basis for the multipole and local expansions, rather
than the plain Cartesian tensor basis. The two are algebraically identical,
but the compressed basis has :math:`(p+1)^2` coefficients at order
:math:`p` instead of the uncompressed :math:`\binom{p+3}{3}`, which
substantially reduces the operation count of the M2L step - the dominant
cost at high expansion order. See Coles and Bieri [3]_ for the derivation of
the reduction fmmgen implements. Because the two bases are algebraically
equivalent, ``tests/test_demag_fmm.py`` checks the compressed path directly
against the FFT-based ``Demag`` (and, for a brute-force ground truth,
against ``DemagFull``), rather than treating it as a separate approximation
to validate independently.

Usage
-----

``DemagFMM`` is added to a simulation the same way as any other
interaction::

    from fidimag.atomistic import Sim, DemagFMM
    from fidimag.common import CuboidMesh
    import fidimag.common.constant as const

    mesh = CuboidMesh(nx=20, ny=20, nz=20, dx=0.3, dy=0.3, dz=0.3,
                       unit_length=1e-9)
    sim = Sim(mesh)
    sim.set_mu_s(2 * const.mu_B)
    sim.add(DemagFMM(order=5, ncrit=128, theta=0.5))

There is no separate driver keyword to pick ``DemagFMM`` over ``Demag`` -
they are both ordinary ``Energy`` interactions, and either or both can be
added to a simulation. ``type='fmm'`` (the default) and ``type='bh'`` select
between the FMM and Barnes-Hut variants described above.

Performance
-----------

.. image:: ../images/demag_fmm_vs_fft.png

``benchmarks/demag_fmm_vs_fft.py`` times a single ``compute_field()`` call
for ``DemagFMM`` against ``Demag``, on cubic :math:`L\times L\times L`
atomistic cuboid meshes, sweeping :math:`L` from 5 to 60 (:math:`N=125` to
:math:`N=216{,}000` spins) and ``theta`` over 0.3, 0.5, 0.7 and 0.9, at
``order=8``, ``ncrit=128``. Both methods' field is already computed for the
timing loop, so their relative L2 difference (against each other, restricted
to nothing here since every site is active) is a free byproduct, recorded as
``field_rel_err`` in the CSV and shown in the bottom panel. See
``benchmarks/results/`` for the raw CSV.

At the smallest size tested (:math:`N=125`), ``DemagFMM`` and ``Demag`` take
about the same time. From there the gap widens steadily with :math:`N`: at
the largest size tested (:math:`N=216{,}000`), ``DemagFMM`` is slower than
``Demag`` by a factor of about 28x at ``theta=0.7`` and about 740x at
``theta=0.3``, and the gap is still widening at that point, not levelling
off. This is not a surprising result: a solid cuboid is exactly the
geometry the FFT convolution is designed for, with full translational
symmetry and no wasted grid sites, so it is a genuinely unfavourable
comparison for the tree method.

Accuracy behaves exactly as ``theta`` is meant to control it: tighter
(smaller) ``theta`` is both slower and more accurate, degrading smoothly
with no surprises, from :math:`5\times10^{-7}` at ``theta=0.3`` up to about
1.1% at ``theta=0.9``, both essentially independent of :math:`N` over the
range tested. ``theta=0.9`` is the only one of the four that is not
comfortably accurate for most purposes; ``0.3`` to ``0.7`` all stay under
0.1%.

Where FMM/Barnes-Hut is worth it
---------------------------------

The FFT method's restriction to a ``CuboidMesh`` is fundamental, not
incidental - the convolution relies on translational symmetry across a
regular grid. ``DemagFMM`` has no such restriction in principle: it operates
on a list of spin positions, not a grid, so it is the natural route to
supporting demagnetising fields on irregular or non-cuboid meshes in the
future.

There is also a more immediate benefit even on ``CuboidMesh``. The FFT
method must pad and transform the full grid, including every non-magnetic
(:math:`\mu_s=0`) site - a patterned sample with large non-magnetic gaps
pays the same grid cost as a solid block of the same bounding box.
``DemagFMM`` does not: ``DemagFMM.setup()`` restricts its tree to the sites
with ``mu_s != 0`` (``np.nonzero(mu_s)``), so its cost tracks the number of
magnetic sites rather than the size of the bounding box they sit in.
``mu_s=0`` sites are simply returned at exactly zero field, since they
carry no moment and never needed one evaluated at them in the first place.

``benchmarks/demag_fmm_vs_fft_sparse.py`` demonstrates this on a fixed
4x4 array of 2.5 nm radius, 3-atomic-layer nanodisks (about 12,800 active
atomistic sites throughout), growing only the spacing between disks, so
the bounding box - and with it the FFT method's grid - grows while the
active site count does not. It sweeps the same ``theta`` values as the
solid-cuboid benchmark above, at ``order=8``. ``benchmarks/plot_nanodisk_array.py``
renders the ``mu_s`` pattern itself; here it is at the 18 nm spacing point
(94% empty):

.. image:: ../images/nanodisk_array_geometry.png

.. image:: ../images/demag_fmm_vs_fft_sparse.png

The x-axis is ``N_grid``, not "sparsity", on purpose: ``Demag``'s cost is a
direct function of the bounding-box grid it convolves over, full stop, with
no notion of how much of that grid is empty. Growing the disk spacing here
grows ``N_grid`` while ``N_active`` stays fixed, which *also* grows the
derived "percent empty" (:math:`1 - N_{\text{active}} / N_{\text{grid}}`)
quoted below - but that is a side effect of the one knob (spacing) being
varied, not an independent cause, so plotting ``Demag``'s time against
emptiness itself would suggest a causal relationship that is not really
there. The bottom panel is the field accuracy, restricted to the active
sites (see the note on ``time_demag`` in the benchmark script for why
inactive sites are excluded from that comparison).

At the smallest spacing tested (6 nm, 45% empty), ``DemagFMM`` is 9x to 55x
slower than ``Demag`` depending on ``theta`` (looser ``theta`` is faster).
The gap closes as the array is spread out, all four ``theta`` curves
crossing ``Demag`` at around 96-97% empty; by the widest spacing tested
(90 nm, 99.8% empty, a :math:`5.27\times10^{6}`-site bounding box),
``DemagFMM`` is 8x to 10x faster than ``Demag``, essentially independent of
``theta`` by that point. This is the geometry - sparse, patterned, or
otherwise mostly-empty samples such as nanomagnet or MRAM bit arrays - the
``mu_s=0`` exclusion is actually for.

Accuracy (bottom panel) stays comfortably good throughout: worst case
across the whole sweep is 0.17% (``theta=0.9``, smallest spacing tested),
and ``theta <= 0.7`` never exceeds 0.01%. It is, if anything, slightly
better than the equivalent solid-cuboid ``theta`` in the Performance section
above (1.1% at ``theta=0.9`` there) - each disk is a small, separate
cluster rather than one large connected block, so the net moment any single
tree cell accumulates is smaller, which is what a geometric acceptance
criterion like ``theta`` responds well to.

One caveat: this only benefits the field evaluation. ``CuboidMesh``
construction itself (in particular its neighbour list, needed regardless of
which demag method is used) still costs :math:`O(\text{bounding box size})`
and does not benefit from sparsity - at the widest spacing tested it took
tens of seconds by itself, far more than either demag call. This is a
one-off cost at ``Sim`` setup, not paid on every ``compute_field()`` call,
so it does not affect the timings above, but it means very sparse samples
with a very large bounding box are not free to set up even once the field
evaluation itself is fast.

While benchmarking this, ``Sim.set_mu_s()`` - which every sparse sample
must call - turned out to have its own, worse-than-the-mesh-construction
cost: it used to redo a full scan of the mesh's neighbour array for every
single ``mu_s=0`` site, an :math:`O(n_{\text{zero}} \times n)` loop. That
made it unusable long before this benchmark's field-evaluation comparison
became relevant (tens of seconds even at a few hundred thousand sites, far
worse at the sizes above). This has been fixed to a single vectorised pass
over the neighbour array, independent of how many sites are zero.

2D systems
----------

A 2D system is simply a ``CuboidMesh`` with ``nz=1``. Every site then sits
at the same z coordinate, so only relative (x, y) displacements ever enter
the field calculation between them - the tree does not need a z column at
all, whatever that shared z actually is. fmmgen has a planar operator
variant for exactly this (``generate_code(..., planar=True)``), which drops
the multipole/local terms that are always zero for z=0 sources and targets;
this is not an approximation, since a 2D mesh's sites genuinely satisfy
that condition. ``DemagFMM.setup()`` detects ``mesh.nz == 1`` and routes to
it automatically, through ``fidimag.extensions.fmm.FMM2D`` rather than the
general ``FMM`` used for a 3D mesh - no separate argument is needed to ask
for it.

.. image:: ../images/demag_fmm_2d_vs_general.png

``benchmarks/demag_fmm_2d_vs_general.py`` times ``FMM2D`` against ``FMM``
called directly on the same 2D mesh's coordinates (forcing the general path
a 3D mesh would otherwise take), for :math:`L \times L` meshes up to
:math:`N=22{,}500`. The planar variant is consistently faster, by 1.3x to
1.7x depending on ``theta``, with no clear trend against :math:`N` over the
range tested - the reduction is in operation count per interaction, not
algorithmic complexity, so the speedup is closer to a constant factor than
a growing one. The two disagree by no more than :math:`2\times10^{-4}`
across the sweep, consistent with both being correct to the same
:math:`(\text{order}, \theta)`-limited approximation error rather than
either being a further approximation of the other.

One caveat found while wiring this in: ``fmm_select()``'s target is a
single process-global pointer that ``compute_field_fmm``/``bh``/``exact``
read at *call* time, not at tree-build time. A 2D and a 3D ``DemagFMM`` can
both be alive in the same process - unremarkable in a test suite, or any
script that runs more than one simulation - and without re-selecting the
right variant on every call, whichever was selected most recently would
silently apply to both. ``FMM``/``FMM2D`` handle this by re-selecting their
own variant immediately before every ``compute_field``/``compute_field_exact``
call rather than only once at construction;
``test_demag_fmm_2D_and_3D_interleaved_do_not_interfere`` in
``tests/test_demag_fmm.py`` is a regression test for it.
